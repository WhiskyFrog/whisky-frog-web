# Hide public cask facet groups in both supported renderers

## Objective

Hide the public facet groups keyed `cask_family`, `cask_type`, and
`cask_material` in both the structured v2 `ProductFacetPanel` and legacy
`ProductFacetSidebar`. Apply a clear presentation-only visibility policy so
the groups remain absent even when responses contain populated, selected, or
relevant cask data, while all non-cask controls and the existing query/API
contract continue to work. Add focused fixture-driven regression evidence for
both renderers, including a recorded reproduction of the pre-correction
failure.

This Task requires approval because it removes three currently visible filter
groups from both public catalog filtering modes.

## Acceptance Criteria

- `ProductFacetPanel` does not render a terms/range section, accessible group
  name, option, count, dependency label, or selected-value control for any
  response group whose stable key is exactly `cask_family`, `cask_type`, or
  `cask_material`.
- The structured exclusion works regardless of server label, response order,
  option count, `relevant`, `selected`, dependency parents, or retained view
  state. It does not use Korean/English label matching and does not suppress
  unfamiliar non-cask keys.
- `ProductFacetSidebar` does not render its `캐스크`, `캐스크 타입`, or
  `캐스크 재질` sections or their options when the corresponding legacy arrays
  are populated and the response `axes` includes all three keys.
- Representative non-cask terms and range controls remain present and
  operable in both renderers, including scope-specific market controls where
  supplied. Reset still clears the caller-owned selection state.
- The cask fields remain in `ProductFilters`, `EMPTY_FILTERS`, normalized query
  state, legacy adapters, API request serialization, response contract aliases,
  fixtures, and `app/lib/api/types.gen.ts`. No backend/API operation, generated
  union/key type, query parameter, or request-parity behavior is deleted or
  narrowed.
- An existing deep link or caller state containing a cask selection continues
  to parse and serialize according to current behavior, contributes to the
  existing resettable state, and can be cleared by the global reset. The hidden
  drawer does not provide a control for adding or changing that selection.
- A single shared public visibility-key definition or equivalently explicit
  and test-covered boundary prevents the two renderers from drifting, without
  moving presentation policy into generated contract code.
- Focused tests use populated data for all three cask keys. They are shown to
  fail against the pre-correction renderers because cask groups/options are
  exposed, then pass after the correction; both outcomes are recorded in
  Implementer Verification.
- Structured component tests assert absence by stable cask keys and
  user-observable labels/options, and positively exercise generic rendering
  with an unfamiliar non-cask group. Any existing generic-renderer fixture
  that uses `cask_type` is changed to a non-cask example rather than weakened
  or removed.
- Legacy component or page-level DOM tests open the drawer with all three cask
  axes populated, assert the three sections and options are absent, and assert
  representative non-cask sections remain. The test does not depend on a live
  backend.
- Existing query serialization and request-parity tests continue to cover the
  three cask parameters, proving that hiding controls did not mutate the
  transport contract.
- `npm test`, `npm run e2e:homepage`, and `npm run build` pass, with commands
  and outcomes recorded in Implementer Verification.

## Constraints

- Do not edit the backend, regenerate or manually patch API types, delete cask
  response fields, remove cask query parameters, or change public request
  payloads.
- Do not hide all dynamically supplied v2 groups, filter by display-label
  text, or hardcode an allowlist that would discard future non-cask facets.
- Do not remove or weaken non-cask facet, query round-trip, request-parity,
  accessibility, drawer focus, catalog, or per-market assertions.
- Do not remove cask metadata from product cards/tables or change admin
  whisky/cask management; only the three public facet groups are in scope.
- Do not make tests depend on empty cask arrays, a live backend, production
  data, credentials, or screenshots alone.

## Context

`app/components/ProductFacetPanel.tsx` currently passes every group from the
structured response through `buildFacetGroupViewModels` and maps every
resulting group to a rendered section. `app/components/ProductFacetSidebar.tsx`
has separate JSX blocks for `cask_family`, `cask_type`, and `cask_material`
whenever their arrays are non-empty and their axes are enabled. Current shared
fixtures leave the legacy cask arrays empty, so they cannot catch the exposure,
and `tests/facet-panel.test.tsx` intentionally uses `cask_type` as its
unfamiliar generic group, which must be replaced by an unfamiliar non-cask key
while retaining the generic-rendering proof. The query model and generated
types reference the three cask keys in many places and are explicitly outside
this presentation-only correction.

### Attempt 1

#### Summary

Completed the presentation-only correction hiding the three public cask facet groups (cask_family/cask_type/cask_material) in both renderers via a shared app/lib/facet-visibility.ts (PUBLIC_HIDDEN_FACET_KEYS/isPublicHiddenFacetKey), consumed by ProductFacetPanel.tsx (filters buildFacetGroupViewModels output by stable key, after view-model construction so labels/options/counts/dependency breadcrumbs for those keys never render) and ProductFacetSidebar.tsx (axisOn() now also excludes the hidden-key set, gating all three JSX section blocks). ProductFilters/EMPTY_FILTERS, normalized query state, legacy adapters, request serialization, response aliases, fixtures, and types.gen.ts are untouched. Test fixtures (catalogFacetV2FixtureWithCask, legacyCatalogFacetFixtureWithCask) add all three cask keys fully populated, reordered, selected, with a dependency-parent chain, and irrelevant/relevant mixes. New structured (facet-panel.test.tsx) and legacy (catalog-page.test.tsx) tests assert absence by stable key/label/option, prove non-cask/generic-key rendering is unaffected (replaced the old cask_type-as-generic-example with experimental_finish, per the task's explicit requirement), and prove a deep-link/caller-owned cask selection still parses, serializes, counts toward the reset badge, and is cleared by global reset without the hidden drawer offering a way to add/change it. product-query.test.mts and request-parity.test.mts gained explicit cases confirming the three cask query parameters still round-trip and match request-parity byte-for-byte. While producing the required pre-correction failure reproduction, I found and fixed a footgun in the new absence assertions: `assert.equal(domNode, null)` is fine when it passes, but on failure (i.e., exactly the pre-correction case) forces Node's assert module to util.inspect a live jsdom node for the diff message, which is pathologically slow (the initial pre-correction run took 300s+ and got SIGKILLed). Added a 3-line `assertAbsent(x)` helper (compares `x === null` as a boolean) in both test files so the demonstration fails fast and legibly instead of hanging.

#### Verification

Post-correction: `npm test` (tsc --noEmit + node --test) → 132/132 pass. `npm run build` → succeeds, all 12 routes generated. `npm run e2e:homepage` → 6/6 pass (narrow/wide TopNav containment, focus, reduced-motion). `git diff --check` → clean, no whitespace errors. No commits made; working tree left with all changes unstaged as found.
